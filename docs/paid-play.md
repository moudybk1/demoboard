# Paid play: authoritative matches and settlement

Paid lobby slots (`MNP-1`–`MNP-4`, `LUD-1`–`LUD-4`) use the existing `/api/{game}/rooms/{roomId}` state and action URLs. Their authoritative state is separate from the older BOARD ledger rooms: entry and settlement for paid play use native ETH.

## Ludo-only launch

`src/lib/game-availability.ts` is the shared launch gate: Ludo is enabled and Monopoly is disabled. The homepage and lobby mark Monopoly “Work in progress”; Play defaults to Ludo, including old Monopoly links. New paid and legacy Monopoly joins, wallet payment prompts, and ready/start requests are blocked.

Do not delete Monopoly tables or block their settlement routes. Existing paid entries remain recoverable, waiting seats can leave for a refund, and matches already started can finish and settle. A verified late entry from a stale client is consumed once and queued for refund instead of opening a seat. A queued refund is not a confirmed payment. Public lobby listings omit Monopoly tables except a viewer's own existing entry.

## Run and deploy

- Run `npm run test:paid-play` and `npm run test:ludo-rules` for isolated regression tests. All chain calls are mocked; the suites cannot send real transactions. To exercise PostgreSQL, start a disposable local cluster and set only `BOARD_TEST_PG_PORT` for `npm run test:paid-play` and `npm run test:wallet-security`. These tests create and drop their own generated-name databases on 127.0.0.1, never use the shell's DATABASE_URL, and must not be pointed at a real database server. `npx tsx src/lib/game/game-rules.check.ts` covers shared board rules too.
- After backup and release approval, apply `npm run db:migrate` to the intended database before deploying. Migration `0012_play_documents` adds durable game/payment documents. Migration `0013_wild_ares` adds wallet ownership provenance and session wallet addresses, quarantines ALL pre-existing wallet accounts, and revokes their old sessions. It preserves balances, wallets, matches and payment records. It also aligns the previously missing buyback enum value with the ledger schema; this does not execute a buyback.
- Production requires `DATABASE_URL` and a stable `PLAY_TREASURY_PRIVATE_KEY`. Keep the existing treasury key when upgrading. Local development without a database uses atomic files and locks in `.data`; do not share that directory or commit its private key.
- A database with no `play-tables` document now FAILS CLOSED. Stop the old web/worker processes and back up their financial files. Run `npm run play:import-store -- --source-dir <backed-up-data-directory> --confirm-chain-id <source-chain-id> --confirm-treasury <source-treasury-address>` with the intended database/network/key injected. The importer copies only table, nonce and payout documents, preserves consumed hashes/refunds/matches, and refuses overwrites. It never copies treasury private-key files or broadcasts funds. For a genuinely new deployment use `--new-ledger` instead of `--source-dir`, with both confirmations; do not use this option to evade reconciliation of an old deployment.
- Cutover records the next chain block. An unknown payment mined before it cannot create a new seat/refund, even after moving to another database. Imported existing seats remain recoverable without re-verifying them as new entries. Historical refund rows without a stable payment identity are held as `review`, preserving their records and pausing new entries until manually reconciled. Do not erase a consumed hash, lower the cutoff, or reset the financial documents to retry a payment.
- Run `npm run play:worker` as a supervised long-lived process with the SAME injected database, treasury and network configuration as the web application. It does not load environment files. Its gameplay loop runs every second; its payment loop reconciles saved transfers, refunds and winners separately. Restart the process on failure and alert on stale heartbeat, insufficient gas or transfer failures. A request-lifetime callback is not a substitute for this worker.
- New entry prompts require fresh gameplay/payment heartbeats and a gas-funded treasury. Mainnet additionally requires explicit `PLAY_MAINNET_ENABLED=true`; leave it unset until release gates below are complete. This flag is not an audit or a certification. Changing the chain or treasury against existing paid storage is rejected; use separate testnet/mainnet databases and never relabel old money.
- Existing local-only browser boards are not imported as trustworthy outcomes. An imported playing table without a server match is cancelled into one full refund intent per funded human; it must never forfeit those funds merely because its board cannot resume. Completed authoritative server matches remain addressable at `/room/{tableId}?match={matchId}` after lobby reuse.
- When moving from the previous file-backed deployment to Postgres, first finish/reconcile existing paid tables, payments and queued refunds. The migration does not silently import an instance's ephemeral files. Preserve the old treasury and payment records for reconciliation.

## Entry and turns

The wallet signs in through the existing challenge/session API. A transaction hash or public address alone cannot control another player's seat. The browser saves an unresolved payment hash, waits for a receipt and opens the room only after `/api/play/sit` verifies the transfer and returns the seat. A failed ready request never creates a local match.

Four distinct funded human seats must all be ready before one persisted match starts. Unready seats expire after two minutes; all remaining waiting entries expire after five minutes from the first seat. Release and full-refund intent commit together. No paid bots are inserted. Every action includes match ID and observed version; the server rejects stale versions, wrong players and illegal moves. Secure server dice determine results; local dice flickering is cosmetic. The worker advances deadlines with no browser traffic and catches up after a restart. The authenticated recover endpoint returns only an existing seat, without scanning or spending payments. Losing sessionStorage no longer removes ready/leave controls.

The published ruleset in `src/lib/game/ludo-launch-rules.ts` describes 52-square BOARD Ludo v2, exact-count home entry, safe squares/blockades, extra rolls, third-six penalty, and 15-second decision deadlines with three cumulative misses. Existing server Ludo snapshots without a version retain v1's 56-square geometry. New entry through the old BOARD-ledger room API is retired; it must not bypass the four-human ETH flow. Legacy BOARD match recovery/settlement is not migrated into this worker and requires an operator-reviewed plan.

Four verified 0.002 ETH entries form 0.008 ETH. Integer wei arithmetic retains 0.00016 ETH (2%) in the operator treasury and sends 0.00784 ETH to the winner. This repository contains no game escrow contract. There is no automatic native-entry fee split, buyback or burn. Entry gas is paid by the player; refund/payout gas is paid by the operator in addition to the amounts owed. Server randomness is not a VRF or independently verifiable on-chain randomness.

## Settlement

The server derives the winner and stores the amount, recipient and settlement status with the match. The result screen requests settlement and polls while it is submitted. It labels a payout confirmed only after a successful chain receipt; a reverted receipt stays failed. A treasury funding/preparation failure offers an explicit retry.

Short, non-nested database transactions reserve a shared treasury nonce and persist signed bytes before broadcast. Contending document locks release their pool connection while waiting. Retries reuse the same signed transaction/hash; its recipient, amount, chain, nonce, signer and hash are checked. Refunds remain in history as queued/submitted/confirmed/failed; broadcast success alone is never completion. Confirmed results cannot be downgraded by a stale worker. `/play/history` links saved results and payment receipts after lobby reuse.

The worker rebroadcasts journal reservations in nonce order, including a crash between reservation and broadcast. Missing receipts never authorize a fresh nonce or duplicate payment. Reverted, underpriced, externally consumed or irrecoverably dropped nonces need operator reconciliation; automatic fee replacement is NOT implemented. Preserve every signed intent and hash. Never delete a journal row or reset its nonce as a retry strategy.

## Legacy ownership review and release gates

Fresh accounts use expiring single-use wallet proofs. Linking proofs include the destination account and a distinct purpose; unverified reservations never select a login account or change a primary payment destination. A legitimate secondary-wallet login remains supported. Historical verified links are not trusted merely because they have a verified timestamp.

Do not bulk clear `wallet_security_hold` or set ownership_version=2. Review each legacy account's independent ownership evidence, other linked wallets, sessions, balance ledger and match history; resolve ambiguous associations without transferring another person's balances. The patch intentionally provides no self-service switch that trusts the same potentially poisoned association. Back up before migration. Existing records are not deleted; restoring an old vulnerable app/schema is not a safe rollback for reopening paid entry.

Before mainnet: resolve legacy account/match recovery; run four independent real testnet wallets through entry, reconnect, expiry refund, normal finish, forfeit and confirmed payout; validate process restarts and RPC outages in the intended deployment; reconcile treasury liabilities and gas reserves; choose and validate a chain-finality policy; obtain an independent security assessment and approved operating/legal terms. Current terms are drafts. Neither unit tests nor the mainnet flag completes those gates.

Live wallet signing and on-chain entry/payout transfers still require an end-to-end check on the intended chain. Unit tests do not prove the deployed treasury has funds or that the RPC provider is available.
